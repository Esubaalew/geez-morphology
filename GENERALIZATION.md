# Generalization: Universal Mechanism, Language-Specific Parameters

## 1. Thesis Statement

Semitic root-and-pattern morphology is generated by a **universal
interdigitation mechanism** parameterized by **language-specific**
inventories. The mechanism: ordered root consonants mapped into slots of
an abstract pattern template. The parameters: consonant inventory, vowel
inventory, pattern templates, script rendering function.

## 2. The Universal Core

### 2.1 Interdigitation

Root consonants maintain relative order when mapped into pattern slots.
This holds for Ge'ez, Arabic (k-t-b -> kataba), Hebrew (k-t-b -> katav),
Amharic, Aramaic, all Semitic languages.

### 2.2 Root as Ordered Tuple

Order matters; (q,t,l) != (t,q,l). The engine treats roots as tuples.

### 2.3 Pattern as Slot Sequence

| Category | Ge'ez | Arabic | Hebrew |
|----------|-------|--------|--------|
| Basic past 3ms | C0a-C1a-C2a | C0a-C1a-C2a | C0a-C1a-C2 |
| Present 3ms | [y]-C0a-C1I-C2I | [ya]-C0C1u-C2u | [y]-C0i-C1C2o |
| Causative | [a]-C0I-C1a-C2a | [a]-C0C1a-C2a | [h]-C0i-C1C2i |

Abstract similarity reflects common Afro-Asiatic inheritance.

### 2.4 Affixation as Fixed Material

Prefixes and suffixes are ("F", text) slots. The engine does not
distinguish affix from pattern-internal fixed segment (simplification;
see limitations).

## 3. Language-Specific Parameters

### 3.1 Script Rendering

| Language | Rendering |
|----------|-----------|
| Ge'ez | (consonant, vowel) -> single Ethiopic syllable via Unicode arithmetic |
| Arabic | consonant letter + diacritic |
| Hebrew | consonant letter + niqqud |

Ge'ez fuses C+V into one codepoint (simple arithmetic). Arabic/Hebrew
need multi-character output per slot. The abstract operation is identical.

### 3.2 Vowel Inventory

| Language | Distinctions |
|----------|--------------|
| Ge'ez | 7 orders |
| Arabic | 3 short + 3 long + diphthongs |
| Hebrew | 7+ qualities |

Engine vowel labels are abstract strings; the count does not matter.

### 3.3 Verb Classes

Ge'ez: Type A (ቀተለ) vs Type B (ባረке) — C0 vowel melody.
Arabic: Form I sub-classes (kataba/yaqtubu vs shariba/yashrabu).
Hebrew: binyanim with characteristic vowels.

**General principle**: Verb class conditions the vowel melody on the
template. The learner handles this via the verb_type feature.

## 4. Not Handled

1. Non-concatenative allomorphy beyond interdigitation (reduplication,
   metathesis).
2. Phonological rules (assimilation, deletion, epenthesis).
3. Weak verb phonology (flagged, not modeled).
4. Prosodic templates (linear slots suffice for generation).

## 5. Toward a Universal Semitic Engine

Would need:
1. Abstract feature geometry (phonological features, not symbols).
2. Ordered rewrite rules post-interdigitation.
3. Pattern inheritance hierarchies.
4. Multi-tier representation (autosegmental).

Current engine is a **generative baseline**: correct core interdigitation
for strong verbs, framework for extensions. Contribution is architectural
clarity (universal mechanism vs language parameters), not full coverage.

## 6. Implications for Neural Models

1. **Tokenization must respect root-pattern split.** BPE destroys roots.
   Use morphological tokenization or character-level models.
2. **Compositional test is the right evaluation.** Train on some roots,
   test on unseen roots. Memorization != learning morphology.
3. **Synthetic data is legitimate.** The generative process is known and
   rule-governed; generating millions of training examples teaches the
   actual linguistic competence.
4. **Engine as teacher.** Use rule-based generator for training data,
   distill into neural model.

## 7. Conclusion

Interdigitation is universal. Ge'ez configuration is one parameterization.
The pattern learner discovers parameters from data. This separation makes
the linguistic hypothesis computationally explicit and testable.

Future: Arabic/Hebrew data, phonological rewrite component, synthetic
data generation for neural training.
